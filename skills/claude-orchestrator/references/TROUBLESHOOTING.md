# Troubleshooting

Common issues, their root causes, and how to fix them.

---

## ByteRover loop not firing in sub-agent output

**Symptom:** A generated agent's response has no `## Memory` section, or the agent skips `brv search` entirely.

**Cause:** The agent followed its task instructions but didn't execute the mandatory loop steps.

**Fix:**
1. Check that the agent file contains `<!-- BEGIN BYTEROVER LOOP -->` — if missing, `byterover_enabled` was `false` at generation time. Run `/update-claude-orchestrator` to regenerate with the loop.
2. If the loop block is present but the agent skipped it: re-invoke and explicitly say "follow the ByteRover memory loop — run `brv search` first before doing any work."
3. If `brv` is not on PATH at run time (e.g., different shell): install via `npm install -g byterover-cli` and ensure it's in your PATH. The orchestrating session will warn in its final report if sub-agents are missing `## Memory` sections.

## `brv curate` appears to hang

**Symptom:** A sub-agent is stuck waiting — the plan step never completes.

**Cause:** The `byterover_loop_fragment.md.tmpl` says never use `--detach`. If the ByteRover daemon is slow or the content is large, `brv curate` can take several seconds.

**Fix:**
- Wait up to 30 seconds before assuming a hang.
- If it's genuinely stuck: kill the sub-agent, check `brv status` for connection issues, then re-run the plan step.
- If it hangs consistently: add `--timeout 10` to the `brv curate` call in the affected agent. Document in `TROUBLESHOOTING.md` (or curate a note to `orchestration/failures/`).
- Remember: `curate` errors are non-fatal — the agent should log `curate: failed — <reason>` and continue rather than blocking the plan.

## User-edited agent file preserved on regenerate

**Symptom:** `/update-claude-orchestrator` reports "skipped (user-edited)" for an agent file.

**Cause:** The file's current SHA doesn't match the SHA stored in `.claude-orchestrator-installed`. This means the file was manually modified after generation.

**Fix:**
- To regenerate and **discard** your edits: delete the file, then run `/update-claude-orchestrator` again.
- To **keep** your edits and register the new SHA: do nothing — the warning is informational. On the next regenerate, the stored SHA will be updated to the current content.
- To see exactly what changed: `git diff .claude/agents/<filename>.md` (if tracked in git).

## Pre-existing agent name conflict

**Symptom:** Q8 (roster confirmation) shows "Agent `foo.md` already exists — not generated by this orchestrator."

**Cause:** A `.claude/agents/foo.md` file was present before the orchestrator was set up. It's registered in `registered_existing_agents` in the marker and will never be clobbered.

**Options:**
- **Keep existing** — don't generate a new agent with that name. The existing agent stays and will be used by the orchestrating session for scope-matched todos.
- **Rename proposed** — generate the new agent under a different name (e.g., `wi-be-domain-modeler-v2`).
- **Skip proposed** — don't generate a project agent for that role; fall back to `impl-<tier>` for those todos.

To unregister an existing agent (let the orchestrator overwrite it): remove its entry from `registered_existing_agents` in `.claude-orchestrator-installed` and run `/update-claude-orchestrator`.

## Fingerprint false-positive on `/update-claude-orchestrator`

**Symptom:** `/update-claude-orchestrator` says the codebase changed (fingerprint mismatch) even when you haven't added any new frameworks or dependencies.

**Cause:** The fingerprint covers `package.json`, `pyproject.toml`, `Cargo.toml`, `go.mod`, `prisma/schema.prisma`, `nest-cli.json`, `turbo.json`, `pnpm-workspace.yaml`. Changes to any of these (including version bumps, script additions, etc.) will change the fingerprint.

**Fix:**
- Review the proposed changes. If the new signals are real (e.g., Prisma was added), accept the proposed agents.
- If the fingerprint changed for unrelated reasons (script update, version bump), you can decline the proposed agents in Q8 without affecting existing agents.

## Plan `execution:` block missing

**Symptom:** `/claude-orchestrate <plan>` errors or the orchestrator stops and asks how to run the plan.

**Cause:** The plan file was saved without an `execution:` block in the YAML frontmatter.

**Fix:** Edit the plan file and add the `execution:` block. Minimum required:

```yaml
execution:
  implementation_model: sonnet
```

See [PLAN_FORMAT.md](PLAN_FORMAT.md) for the full schema.

## Plan file confusion across projects

**Symptom:** `/claude-orchestrate-resume` resumes the wrong plan, or plan files from different projects are hard to distinguish.

**Cause:** Plan files live at `~/.claude/plans/` — a user-wide directory. If you work on multiple projects and all plans are named `plan.md`, they'll collide.

**Fix:** Use project-prefixed plan filenames:
- `~/.claude/plans/wi-be-payment-module.md`
- `~/.claude/plans/my-app-auth-refactor.md`

The skill always refers to plans by their full path, so `/claude-orchestrate ~/.claude/plans/wi-be-payment-module.md` is unambiguous.

## ByteRover `brv query` called by sub-agent (expensive)

**Symptom:** Cost is higher than expected; a sub-agent's `## Memory` section shows it used `brv query`.

**Cause:** A sub-agent called `brv query` instead of `brv search`. Only the orchestrating session (the one running `/claude-orchestrate`) may call `brv query` (costs an LLM call). Sub-agents must use `brv search` only (BM25, free).

**Fix:** Re-read the sub-agent's file and verify the ByteRover loop says "Do NOT call `brv query`." If the agent is user-edited and that instruction was removed, re-add it or regenerate.

## `analyze_codebase.py` is slow on a large monorepo

**Symptom:** Codebase analysis takes more than 30 seconds; the script prints a timeout warning.

**Cause:** The glob patterns for architectural signals scan the full tree. On very large repos with many modules, this can exceed the 30-second soft limit.

**Fix:**
1. The script skips `node_modules/`, `.git/`, `dist/`, `build/`, `.next/`, `target/`, `.venv/` by default.
2. If you have other large generated directories, add them to the skip list by editing `SKIP_DIRS` at the top of `scripts/analyze_codebase.py`.
3. Alternatively, pass `--max-files 50` to reduce the per-signal cap (default 100).

## `brv` not found after `npm install -g byterover-cli`

**Symptom:** `detect_byterover.py` still returns `"installed": false` even after global npm install.

**Cause:** The npm global `bin` directory is not on PATH in the shell where Claude Code is running.

**Fix:**
1. Run `! npm root -g` to find the global prefix.
2. Add `<prefix>/bin` to PATH in your shell profile (`.zshrc`, `.bashrc`, etc.).
3. Open a new terminal session (or run `source ~/.zshrc`) so the new PATH takes effect.
4. Verify: `! brv --version`
5. Then re-run `/update-claude-orchestrator` — it will detect `brv` and offer to regenerate agents with the loop.

## Agent returned without updating todo status

**Symptom:** A todo in the plan file shows `in_progress` but the sub-agent has finished and returned.

**Cause:** The orchestrating session is responsible for updating todo statuses — it updates `pending → in_progress → completed` around each dispatch. If orchestration was interrupted mid-step, the status may be stuck.

**Fix:** Use `/claude-orchestrate-resume <plan>` — it reads the plan, finds the first `pending` or `in_progress` todo, and resumes from there. The resume command will update the status correctly on completion.

---

## Orchestration spawns a separate agent / loses planning context

**Symptom:** Running `/claude-orchestrate` starts a fresh `plan-orchestrator` sub-agent that knows nothing about the planning conversation.

**Cause:** A pre-refactor install. Older versions shipped a `plan-orchestrator` sub-agent (`.claude/agents/plan-orchestrator.md`) that the command delegated to. Sub-agents always run in an isolated context, so the planning context was lost. Current versions make the session that runs the command the orchestrator.

**Fix:** Run `/update-claude-orchestrator` to regenerate. The obsolete `plan-orchestrator.md` is removed automatically (or preserved with a warning if you edited it — delete it manually, then re-run). The refreshed `/claude-orchestrate` command and `references/ORCHESTRATION.md` make the current session dispatch each step directly.
